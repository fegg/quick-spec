# EARS 写作与评审指南

在 Requirements 阶段读取；设计或任务阶段需要核对语义与追溯时回看。

## 方法边界与来源

EARS（Easy Approach to Requirements Syntax）约束自然语言需求的句子结构。模式及关键字依据 [Alistair Mavin 的 EARS 官方指南](https://alistairmavin.com/ears/)。以下中文表达和软件示例是本 skill 的应用约定，不是官方译文。

EARS 不替代需求访谈、领域判断或人工批准。用户故事表达角色与价值，EARS 表达系统义务，测试用例验证具体实例。背景、范围、术语、设计决策和开放问题不需要硬套句式。

## 模式选择

按需求含义选择，不要求每份文档凑齐全部模式。句中使用具体的系统或组件名称；“应”表示必须满足的义务，不是可选建议。

| 模式 | 关键字 | 中文写法 |
| --- | --- | --- |
| 常驻 | SHALL | `<主体>应<结果>。` |
| 事件驱动 | WHEN | `当<事件发生>时，<主体>应<结果>。` |
| 状态驱动 | WHILE | `在<状态持续成立>期间，<主体>应<结果>。` |
| 异常响应 | IF / THEN | `如果<不期望的条件或事件>，则<主体>应<处理结果>。` |
| 可选功能 | WHERE | `对于包含<可选功能>的<产品或配置>，<主体>应<结果>。` |
| 组合 | 上述模式组合 | 先写可选配置与持续状态，再写正常事件或异常条件，最后写主体与结果。 |

`WHEN` 描述发生的一刻，`WHILE` 描述持续区间；“进入加载状态”与“处于加载状态”不能互换。`WHERE` 是某产品或配置具备可选能力，不是地理位置、任意业务前提，也不是“需求可以不做”。正常触发使用 `WHEN`，不把所有条件都写成异常 `IF`。

组合条件用于限制同一个响应的适用范围，例如“在编辑请求处理中，当用户再次点击保存时，编辑页面应忽略本次点击”。独立触发的行为应拆开；多个条件明确是同时满足还是任一满足，避免含糊的“和/或”。不为拆句丢掉共享前提。

## 从意图到可验证条目

1. 提取已确认的角色、主体、行为、条件及来源。把冲突或缺失信息列为 `Qn`，建议必须与事实区分。
2. 选择最简单且准确的模式，尽量让一条编号对应一个独立可验证结果。这是 quick-spec 的粒度约定，不声称 EARS 原法只允许一个响应。
3. 结果应能通过界面、数据、响应、日志或量化测量观察。将“快速、合理、友好、正确处理”改为有依据的判定；未知阈值保持待确认，不能自定。
4. 对状态起止、条件边界、主体责任和术语检查歧义；只对确实存在缺口的地方提问。
5. 为条目记录来源、验证方式和未确认项。修改句式不得扩大原目标，示例中的行为与数值不能自动成为业务要求。

以下是假设已确认的示例，各自独立，不是默认功能清单：

- 常驻：报表页面应以 UTC 显示记录时间。
- 事件：当用户点击清空筛选时，列表页面应将筛选条件恢复为已定义的初始值。
- 状态：在保存请求未结束期间，编辑页面应禁用保存按钮。
- 异常：如果导入文件的必填列缺失，则导入服务应拒绝该文件。
- 可选功能：对于包含 CSV 导出功能的产品版本，报表页面应显示 CSV 导出入口。
- 组合：对于包含 CSV 导出功能的产品版本，在导出任务执行期间，当用户再次请求导出时，导出服务应返回当前任务标识。

反例：“用户点击保存后，系统应快速保存并友好提示，失败时自动重试。”这句话混合多个结果且引入未定阈值和恢复策略。先核实保存结果、提示及重试是否都在范围内，再拆成有来源的条目；未经确认的重试只进入问题列表。

性能、容量等非功能要求也要可测。例如已确认的约束可表达为：“在指定基准环境与固定数据集下，当执行查询时，查询服务应满足 p95 响应时间不超过约定阈值。”必须另列实际环境、数据规模、并发、采样窗口和阈值；缺失时该条仍为未确认。不能只把“性能良好”换成含 SHALL 的句子。

## 评审检查

提交人工评审前，逐条核对并在 requirements 记录结论和未通过项：

- **有依据**：每条能追溯到 intent、明确回复或已核验约束；假设没有伪装为事实。
- **无歧义**：主体、术语、状态、触发及结果明确，组合条件逻辑清楚。
- **可验证**：结果可观察；指标有单位、条件和阈值；禁止行为也有明确适用边界。
- **可追溯**：编号唯一、稳定，设计与任务引用具体条目；变更没有复用旧编号表达新义。
- **范围一致**：核对已声明的正常、异常、边界及状态限制，没有遗漏已知行为或额外发明功能；不适用的模式无需补齐。
- **无冲突**：同一条件下的条目没有互斥响应，需求不与已确认约束矛盾。
- **待决显式**：`【未确认 Qn】` 关联具体问题、影响和建议；下游保留阻塞，不因文档整体批准自动解除。

句式检查通过只是写作检查，不证明需求完整、可实现或已通过业务验收。

## 设计、任务和验证追溯

设计引用 `N.M` 并解释如何满足它；任务引用同一编号。一个需求可以对应多个任务或测试场景，但每条已批准、范围内的标准都必须在覆盖清单中有去向。

将 EARS 映射到 BDD 时：配置与持续状态进入 `Given`，正常事件或异常触发进入 `When`，可观察响应进入 `Then`。常驻约束使用适合的检查动作；持续状态的验证应覆盖该状态持续的区间，不能只测试进入状态的一刻。状态结束后应做什么，必须另有需求依据，不能推断逆命题。

TDD 则用相同配置与状态安排输入，用事件或异常条件驱动被测行为，断言约定结果与必要边界。没有事件的约束可用属性或不变量检查；无法由单测证明的性能、外部集成等约束标明需要的验证层级。

例如需求 `1.1`：“在保存请求未结束期间，编辑页面应禁用保存按钮。”

```gherkin
Feature: 编辑保存
  Scenario: 保存请求尚未结束
    Given 编辑页面已发出保存请求且请求尚未结束
    When 检查请求等待期间保存按钮的状态
    Then 保存按钮处于禁用状态
```

该场景只覆盖 `1.1`；按钮点击是否发请求、保存成功后的行为都需要各自的需求依据。Gherkin 文本是验收场景，不等于已接入测试框架或运行通过。
