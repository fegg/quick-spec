## 一、依据与执行规则

- 依据：[requirements.md](./requirements.md)（已批准）、[design.md](./design.md)（已批准，或“用户明确跳过”）；跳过需求时引用本文件“已确认目标”。
- 验收方式：<TDD / BDD / 结合 / 不编写验收用例>
- 目标工作区与基线：<仓库路径、分支及起始 HEAD；记录未提交改动基线，不擅自回滚无关修改>
- 原子执行与证据门禁：
  - 任务按粒度拆分（建议 1 人日内独立完成并可验证），一次只执行一个任务。
  - 完成后在任务下方补充 `证据：`（记录真实执行命令、测试输出、生成的产物绝对路径或实测截图路径）。
  - **严禁在未真实运行验证前提前勾选 `[x]`**；依赖【未确认 Qn】的任务保持阻塞。
- 模块上下文重注入（多模块/长任务按需）：
  - 切换模块或派发子代理前，先按重注入索引表重新加载对应模块的需求章节、设计分册与契约锚点，刷新上下文注意力，防止长会话注意力衰减。
- 跨会话检查点接力（长任务按需）：
  - 复杂工程按需维护 [handoff.md](./handoff.md) 作为跨会话/子代理唯一状态检查点，记录阶段推进、未提交改动、本地服务端口与下一步。
- 前端先行与环境约束（按需）：
  - 明确隔离 Mock 与真实接口验收；指定实测浏览器/宿主环境与视觉比对基准（如 Figma 节点）。

## 五、BDD 场景（选择 BDD 或 TDD + BDD 时）

用 Gherkin 代码块编写场景，每块包含一个 Feature，可直接转写为一个 `.feature`。场景编号用标签或标题表达；表格仅用于 `Examples:`、步骤数据或独立的需求覆盖清单。待决条件和执行状态写在代码块之外。按实际功能替换下方示例。

```gherkin
Feature: 查看操作记录详情

  @S01
  Scenario: 从列表打开指定记录
    Given 操作记录列表中有一条编号为 OP-123 的记录
    When 用户打开 OP-123 的详情
    Then 详情显示操作编号 OP-123

  @S02
  Scenario Outline: 展示记录的提交动作
    Given 操作记录的提交动作为「<动作>」
    When 用户打开该操作记录的详情
    Then 提交动作区域显示「<展示结果>」

    Examples:
      | 动作    | 展示结果  |
      | 发送通知 | 发送通知  |
      | 空列表   | 无附加动作 |
```
